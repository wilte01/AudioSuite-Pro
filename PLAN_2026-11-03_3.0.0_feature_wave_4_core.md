# PLAN — `3.0.0` Feature Wave 4, core (F-M1, F-M2, F-M4)

**Status:** `[ ]` **NOT STARTED.** Planning complete, 2026-11-03.

**Target release:** `3.0.0`, a **major** by the audit's own definition ("a new
subsystem, not an extension"). Three new subsystems: plugin hosting, an
interactive spectral editor, and a restoration expansion.

**Base state:** `2.7.0` landed. Required predecessors: `2.5.0` (channel utilities
for M/S helpers), `2.7.0` (EQ/dynamics engines, which the plugin chain must sit
beside and the spectral editor's repair report reuses), WP-9 (module splits, so
the new code does not land in 1,200-line files), WP-5 (`audio_probe`, which every
acceptance measurement below uses).

**Governing scope:** F-M1 (VST3/AU hosting and offline chain), F-M2 (interactive
spectral editor/repair), F-M4 (de-crackle, wow/flutter, de-reverb). F-M3, F-M5
and F-M6 are `3.1.0` and decision-gated.

**Why major, and what "major" does not mean here:** nothing in `3.0.0` breaks an
existing workflow. The bump signals a new dependency surface (third-party plugin
binaries, an interactive editor with its own undo) and a new failure mode (a
plugin that crashes). State that in the release notes so users do not assume a
migration.

## 2. F-M1 — VST3/AU plugin hosting and offline chain

### 2.1 The crash-isolation decision (blocking, D-1)

`pedalboard` hosts VST3 in-process. A third-party plugin that segfaults takes
the process with it, and a batch suite cannot accept "one bad plugin kills a
500-file run". Therefore:

- **Rendering runs in a subprocess worker**, one worker per file (or per chunk),
  not in the GUI or the batch process. The parent sends the file path, the chain
  state and the sample buffer (or a temp file path), and receives the processed
  buffer plus a status. A worker crash is a failed *file*, recorded with the
  plugin name, and the batch continues.
- Worker pool size is a setting (default `min(4, cpu_count())`), and the worker
  is a module (`python -m audio_suite_shared.plugin_host.worker`) so it is
  testable in isolation.
- A plugin that times out (per-file wall clock, default 120 s) is treated as a
  crash: the file fails, the plugin is marked unstable for the run, and the
  remaining files skip it with a caveat in `run_outcome`.

### 2.2 Package shape

| File | Content |
|---|---|
| `audio_suite_shared/plugin_host/__init__.py` | Public surface, no side effects |
| `audio_suite_shared/plugin_host/scan.py` | Discover VST3/AU on Windows/macOS: standard directories plus user paths, parse `pedalboard.VST3Plugin` metadata (`name`, vendor, category, parameters), cache to a JSON file keyed by `(path, mtime, size)`. Never import/instantiate during discovery unless required to read metadata — record which it is |
| `audio_suite_shared/plugin_host/chain.py` | `PluginSlot(path, state: bytes, bypass, parameter_overrides)`, `PluginChain(slots)`, validation that every slot resolves to a scanned plugin |
| `audio_suite_shared/plugin_host/state.py` | Serialise per-plugin state (base64) into the preset; round-trip test; version the blob so a plugin update is detected rather than silently mis-loaded |
| `audio_suite_shared/plugin_host/worker.py` | Subprocess entry: render a file, write output, exit non-zero on failure with a structured error line |
| `audio_suite_shared/plugin_host/runner.py` | Parent side: spawn, timeout, collect, map failure to a per-file outcome |
| `audio_refinery/core/plugins.py` | Refinery stage adapter (`StageConfig.plugins: PluginChain | None`) |
| `audio_refinery/ui/plugins_panel.py` | Chain list (add/remove/reorder/bypass), scan button, generic parameter widgets from the plugin's parameter list, "safe mode" toggle |
| `audio_refinery/utils/settings.py` | Persist the chain in `StageConfig`; shipped default is an empty chain |
| `audio_refinery/cli.py` | `--plugin PATH` (repeatable), `--plugin-state FILE`, `--no-plugins` |
| `master_driver/ui/cards/audio_refinery_card.py`, `runner/arg_builder.py` | Chain summary + flags |
| `tests/test_plugin_host_scan.py`, `test_plugin_chain_state.py`, `test_plugin_worker_isolation.py`, `test_plugins_chain_render.py` | The locks |

### 2.3 Acceptance and tests

- **Determinism:** a known VST3 renders byte-identical output across two runs in
  one process and across two worker processes (compare decoded PCM hashes). Use
  a plugin the project can legally bundle for tests, or a stub plugin the test
  builds itself — never a user's licensed plugin, never a downloaded binary
  committed to the repo.
- **Crash isolation:** a deliberately crashing stub worker (raises/aborts in the
  child) fails exactly one file; the batch completes the rest; the report names
  the plugin and the file; `run_outcome` carries the caveat.
- **State round-trip:** chain state saved to the preset, reloaded in a fresh
  process, renders the same output as the in-memory chain.
- **Bypass:** every slot bypassed renders the input unchanged (bit-transparent
  after decode).
- **Scan cache:** adding a plugin directory changes the cache key; a removed
  plugin is reported missing at chain validation, not at render time.
- **No plugin path leaks into a tag, log line or report.**

### 2.4 Risks

1. **Licensing.** Pedalboard is GPL-3.0 and the suite is GPL-3.0, so hosting is
   consistent, but a user's plugins carry their own licences; the guide must say
   the suite ships none.
2. **Parameter UI is unbounded.** Do not attempt a bespoke editor per plugin;
   a generic parameter list with name/range/value and a "save state" button is
   the deliverable.
3. **Cross-platform discovery** (`C:\Program Files\Common Files\VST3`,
   `/Library/Audio/Plug-Ins/VST3`, `~/Library/Audio/Plug-Ins/Components`) must be
   enumerated in one table with tests, not scattered string literals.
4. **A plugin that writes audio during scan** — scanning must never process a
   file; assert no file write during a scan in the test.

### 2.5 Effort

6-10 weeks. This is the largest single item in the audit.

## 3. F-M2 — Interactive spectral editor/repair

### 3.1 Shape: a new tool, not a read-only viewer mode

`spectral_viewer` is advertised as read-only and its manifest says so. Adding
editing would make the same window sometimes write audio, which breaks that
promise and the tool's tests. New tool `spectral_repair`:

| File | Content |
|---|---|
| `spectral_repair/core/stft.py` | STFT/iSTFT with explicit window, hop and padding; `analyse(audio) -> Spectrogram`, `synthesise(spec) -> audio`; round-trip identity within float tolerance |
| `spectral_repair/core/selection.py` | `TimeFreqSelection` (rect, lasso mask), intersection with the bin grid, expand/contract in bins |
| `spectral_repair/core/ops.py` | `attenuate(spec, mask, db)`, `heal(spec, mask, method="interpolate"|"spectral")`, `replace_from(spec, mask, source_spec)`; each returns a new spec plus a `RepairReport` (bins changed, energy removed in the band, neighbouring-bin change) |
| `spectral_repair/core/render.py` | Viewport rendering: decimate to the canvas width with min/max per pixel bucket; never render the full STFT at full resolution |
| `spectral_repair/app.py`, `ui/canvas.py`, `ui/setup_tab.py`, `ui/results_tab.py` | Zoom/pan, selection, op buttons, before/after toggle, undo/redo |
| `spectral_repair/core/undo.py` | The file's original bytes snapshotted through `batch_undo`, so one undo restores the file exactly |
| `spectral_repair/cli.py`, `utils/cli_args.py` | Batch mode for a saved operation (`--op attenuate --band 50-60 --db -12`), so a repair can be repeated across a folder |

`tool_id = "spectral_repair"`, `pyw = Spectral_Repair.pyw`. Reuse
`spectral_viewer/core/spectrogram.py`'s analysis conventions only if they are
extractable without changing the viewer; otherwise share the new `stft.py` and
have the viewer adopt it later (recorded, not forced).

### 3.2 Acceptance and tests

- **Round-trip identity:** `synthesise(analyse(x))` equals `x` within 1e-6
  (float) for a 1 s tone; the written file's decoded samples equal the source
  within 1 LSB.
- **Click removal:** a synthetic click at 1 kHz with a rectangular selection
  removes the target band's energy by at least the requested attenuation while
  neighbouring bins (further than one bin from the mask) change by less than
  0.5 dB. A blind gain change cannot pass this, because the reduction is
  band-local and measured.
- **Hum removal:** a 50 Hz tone plus harmonics attenuated by a band mask reduces
  each harmonic by the requested amount and leaves a 1 kHz tone within 0.2 dB.
- **Undo:** restores the original file bytes (SHA-256 equal), proven on a real
  file, not on a spec.
- **Viewport rendering:** a 10-minute file renders an overview in bounded time
  (assert a wall-clock budget with generous headroom, and that the rendered
  peak envelope matches decoded min/max per pixel bucket within 1 LSB).
- **Dry run / preview:** preview never writes the source file.

### 3.3 Risks

1. **Inverse STFT correctness** is the whole item: a windowed overlap-add with
   the wrong normalisation sounds fine on a tone and destroys real material.
   Test with broadband noise and assert reconstruction error, not just a tone.
2. **Interactive performance:** render the viewport only, cache the analysis,
   and never block the Tk thread — the canvas draws from a prepared array via
   `root.after`.
3. **Undo scope:** one file's repair is one undo batch; a batch repair across a
   folder is one batch with per-file snapshots.

### 3.4 Effort

8-12 weeks.

## 4. F-M4 — Restoration expansion (de-crackle, wow/flutter, de-reverb)

### 4.1 Shape: extend the Restoration tool

The tool already owns "repair a file and report the measured improvement", so it
gains modes rather than becoming three tools:

- `--mode declip|decrackle|wowflutter|dereverb` (default `declip`, so existing
  runs are unchanged), with per-mode settings.
- New modules: `restoration/core/decrackle.py`, `restoration/core/wow_flutter.py`,
  `restoration/core/dereverb.py`, each pure and each returning a
  `RepairMetrics` object.
- GUI: mode selector plus that mode's settings; the results table shows the
  mode's metrics.
- Order within the release: **de-crackle**, then **wow/flutter**, then
  **de-reverb** — the audit's order, chosen because each has a measurable
  reference and de-reverb's is the weakest.

### 4.2 Objective acceptance (the rule the earlier deferral established)

Each sub-item must have a metric that a blind gain change cannot pass:

| Mode | Metric | Acceptance |
|---|---|---|
| De-crackle | Impulse count and peak residual: count samples exceeding a robust threshold above the local median; measure the residual energy in 1 ms windows around detected impulses | Impulse count reduced by >= 90 % on a fixture with N injected clicks; the residual energy at those positions reduced by >= 12 dB; a control region without clicks changes by < 0.5 dB |
| Wow/flutter | Instantaneous pitch track (librosa `pyin` or `piptrack`) over a steady tone; compute the standard deviation of the deviation from the mean | Pitch-drift SD reduced by >= 50 % on a fixture with synthetic 0.5 Hz wow; the mean pitch unchanged within 1 cent; duration unchanged within 1 ms |
| De-reverb | Decay ratio: energy in a late window / early window after an impulse, or EDT from a synthetic impulse response convolved into a dry fixture | Late/early ratio reduced by >= 3 dB; the dry component's spectral tilt within 0.5 dB of the source; no added pre-echo above the noise floor |

Additional rules:

- Every mode reports before/after values from the **rendered** file.
- A mode that cannot measure its own improvement refuses to claim success:
  status is `done` with metrics or `error` with the reason, never "done" with an
  unmeasured claim.
- Dry run reports the projected metrics from an in-memory render.

### 4.3 Tests

- One fixture per mode, built by the test (injected clicks, synthetic wow,
  convolved impulse response), plus one real-audio fixture from the committed
  corpus for sanity (no blind listening claim).
- A negative control for each: the same fixture processed by a plain gain change
  fails the acceptance metric. This is the guard against a metric that measures
  loudness instead of repair.
- Declip's existing tests and thresholds remain untouched; a regression there is
  a release blocker.

### 4.4 Risks

1. **De-reverb is the weakest metric.** If the decay-ratio test cannot be made
   to pass on a synthetic IR without damaging the dry signal, ship de-crackle and
   wow/flutter and defer de-reverb again — with the measured evidence, as the
   earlier deferral did.
2. **Crackle detection conflates musical transients.** The detector must be
   tested on a percussive fixture to show it does not remove drum hits (assert
   transient retention above a bound).
3. **Process order.** A file may need declip then decrackle; the tool applies one
   mode per run, and a chained run is two runs, each undoable.

### 4.5 Effort

6-10 weeks, of which de-reverb is half.

without worker isolation (item 2), and it may not ship a repair mode whose
metric has not been shown to fail for a blind gain change.
