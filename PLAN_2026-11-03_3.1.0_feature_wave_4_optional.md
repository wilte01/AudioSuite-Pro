# PLAN — `3.1.0` Feature Wave 4, optional (F-M3, F-M5, F-M6)

**Status:** `[ ]` **NOT STARTED — decision-gated.** Planning complete,
2026-11-03. §11.2 attaches this release to a product decision, so this plan is
written to be *decidable*, not to be started by default.

**Target release:** `3.1.0`, a **minor** on top of `3.0.0`, with no break to any
`3.0.0` interface.

**Base state:** `3.0.0` landed. F-M3 additionally needs F-S6 (multichannel phase
1), which §11.2 does **not** schedule; if F-S6 has not shipped, F-M3 starts with
it and its effort doubles. That dependency is the first decision in §7.

**Governing scope:** F-M3 (full multichannel/immersive), F-M5 (real-time
monitoring chain), F-M6 (reference matching / assisted mastering).

**Read with:** `PLAN_2026-11-03_audit_sequencing.md` §4.

---

## 1. Why each of these is a decision, not a task

| Item | The decision it forces |
|---|---|
| F-M3 | Is the product a stereo batch tool that tolerates surround files, or a surround authoring tool? The second implies per-layout DSP, downmix matrices and a channel-aware UI across every stage. |
| F-M5 | Is real-time monitoring in scope at all when §10.4 puts playback explicitly out of scope? A monitored *preview* of the configured chain is arguably processing, but it needs an audio device, latency reporting and a live thread model the suite has never had. |
| F-M6 | Does the suite propose mastering moves, or only measure and report? F-S7 already measures; proposing corrections is a different product promise and needs a "never exceed the ceiling, every move explainable and reversible" guarantee. |

The plan below gives each a bounded phase-1 shape and states the evidence that
would justify phase 2. Nothing here should start before that decision is
recorded.

## 2. F-M3 — Full multichannel/immersive pipeline

### 2.1 Phase 0 (prerequisite, currently unscheduled): F-S6

- Decode/encode 5.1/7.1 without downmix; preserve channel count and order.
- A channel map (`FL FR FC LFE SL SR` / `FL FR FC LFE BL BR SL SR`) validated
  against the container's actual layout from `ffprobe`.
- Per-channel peak/RMS in reports.
- Every DSP stage refuses or explicitly downmixes, with a named reason.
- Acceptance: channel order and count survive a convert round-trip (verify by
  rendering a distinct tone per channel and decoding it back per channel); per-
  channel measurements match the source; an unsupported stage refuses.

Files: `audio_suite_shared/audio_formats.py` (channel layout capability per
container), `audio_probe` (`StreamInfo.channel_layout`), `audio_conversion.py`
(packing per channel count), `audio_refinery/core/pipeline.py` (refusal/
downmix policy per stage), `music_format_converter` (pass-through policy),
`library_stats/core/qc.py` (per-channel metrics).

### 2.2 Phase 1: documented downmix/upmix matrices

- `audio_suite_shared/channel_matrix.py`:
  - `DownmixMatrix` (5.1 -> stereo per ITU-R BS.775: `L = FL + 0.707*FC + 0.707*SL`,
    `R = FR + 0.707*FC + 0.707*SR`, LFE excluded by default with a stated reason
    and an explicit `--include-lfe` option);
  - `UpmixMatrix` (stereo -> 5.1) documented as a **decorrelation-free** pass
    (centre and surrounds derived, no invented content) or omitted;
  - `apply_matrix(audio, matrix)` with a headroom rule: normalise so the worst
    case does not clip, and report the attenuation applied.
- Loudness per layout: BS.1770 channel weighting (1.0 for L/R/C, 1.41 for
  surrounds, 0 for LFE) implemented in `audio_probe.measure_loudness` behind a
  `layout` parameter; a stereo default keeps every existing number unchanged.
- CLI/GUI: downmix as a Refinery stage option and in `channel_tools`; the
  results report states the matrix used and the headroom rule.

### 2.3 Acceptance

- A 5.1 fixture with a distinct tone per channel downmixes to a stereo file whose
  per-channel content matches the matrix algebra within 0.1 dB.
- No clipping after the documented headroom rule (true peak at or below the
  configured ceiling).
- Per-layout loudness matches a reference meter's BS.1770 value within 0.5 LU on
  the fixture; the stereo path's numbers are unchanged from `2.7.0` (regression
  lock).
- Channel order survives every supported stage; an unsupported stage refuses
  with a named reason and does not silently downmix.

### 2.4 Risk

BS.1770 for surround has both a "EBU R128" variant (surround weighting) and a
plain channel sum; publishing one number without naming the weighting is how two
tools disagree. Name the standard and the weighting in the column header, and
keep the stereo path bit-identical to the existing implementation.

### 2.5 Effort

6-10 weeks including F-S6.

## 3. F-M5 — Real-time monitoring chain

### 3.1 Preconditions

- An audio output device (`sounddevice` is already a dependency and
  `audio_playback` uses it for audition).
- A defined scope boundary: **preview only, no writes**, and not a player.

### 3.2 Design

- `audio_suite_shared/monitor.py`:
  - `MonitorChain` built from the same stage objects the render path uses (EQ,
    dynamics, plugins) so preview and render cannot diverge by construction;
  - streaming processing in blocks of a fixed size with an explicit latency
    report (`block_size / sample_rate + plugin_latency`);
  - `start(path, at_seconds)`, `stop()`, `latency_ms`, `describe()`.
- Playback thread model: one `sounddevice.OutputStream` callback (or a
  `RawOutputStream` + block loop), never a Tk call; UI updates via a queue and a
  poller the Tk thread started — the `plugins/example_plugin/window.py` rule
  (`PLAN_feature_expansion.md` D136) applies exactly.
- UI: a "Monitor" button in the Refinery, a latency readout, a bypass toggle, and
  a loudness/TP meter fed from the same report objects as the dry run.

### 3.3 Acceptance and tests (headless-safe)

- **Preview equals render:** render the same file offline through `MonitorChain`
  in blocks and through the normal pipeline; decoded outputs match
  sample-for-sample at the same settings.
- **Latency:** reported latency equals the measured round-trip offset in the
  block loop (assert the computed value from the block size and the injected
  plugin latency, and state that a real device loopback is not exercised in CI).
- **No writes:** a full preview run changes no file (`st_mtime_ns` snapshot).
- **Device absence:** without an output device, monitoring refuses with a named
  reason and the tool still works (no import-time device open).
- **Thread safety:** a test asserts no widget method is called from the audio
  thread (the window's queue/poller pattern).

### 3.4 Risk

Real-time audio on Windows with Python callbacks is where "works on my machine"
lives. Phase 1 must be honest: a monitored preview with a reported latency and a
documented "not sample-accurate monitoring" caveat is better than a claim of
zero-latency monitoring. If the block loop cannot keep up on the reference host,
ship the offline A/B (F-S9) only and record the measurement.

### 3.5 Effort

6-8 weeks.

## 4. F-M6 — Reference-matching / assisted mastering

### 4.1 Design (proposal-only)

- `audio_suite_shared/reference.py`:
  - `ReferenceProfile`: integrated LUFS, LRA, true peak, spectral balance in
    third-octave bands, crest factor, stereo width;
  - `compare(target_profile, reference_profile, limits) -> list[Proposal]`,
    where `Proposal` is one of a small closed set: gain change, broad tilt
    (a documented shelf pair, not arbitrary EQ), dynamics change, width change.
  - Every proposal carries its measured basis, the projected outcome and a
    confidence; `limits` caps the total gain, tilt and dynamics move.
- Applying a proposal goes through the existing EQ/dynamics stages, so it is
  reversible and auditable; nothing bypasses them.
- Refuse to propose when the reference is not comparable (different channel
  layout, extreme duration difference, a reference that is itself clipped).

### 4.2 Acceptance

- Applying the proposals to the target moves measured integrated loudness,
  spectral distance and crest factor toward the reference by a measurable
  amount, and the test asserts the **distance decreased**; a no-op proposal set
  is not success.
- Never exceed the configured true-peak ceiling (measured on the render).
- Every proposal is explainable: the report names the metric, the measured
  before/after and the limit applied.
- Reversibility: undo restores the pre-apply bytes.
- A blind gain change cannot pass: a test applies only the gain proposal and
  shows the spectral distance is unchanged, which is the distinction the feature
  claims.

### 4.3 Risk

"Assisted mastering" is a promise users will read as "sounds like the
reference". The plan's language, the guide and the UI must say "moves measured
metrics toward the reference within limits", and the test must measure the
metrics, not a listening impression.

### 4.4 Effort

6-8 weeks.
