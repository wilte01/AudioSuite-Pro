# AudioSuite-Pro

AudioSuite-Pro is a Windows-first audio workbench of 30 first-party tools
that share one driver, one command line and one registry: tag enrichment
(BPM, key, mood, lyrics, album art, ReplayGain, genre), DSP repair and
conversion (loudness normalisation, hum/click removal, silence trimming,
format conversion, enhancement), library utilities (CD ripping, tag-based
reorganisation, statistics) and a full multi-stage refinery pipeline. Every
tool has a generated user guide, a card in the Master Driver control panel,
and an `audiosuite` CLI subcommand where one exists.

## Prerequisites

* **Python 3.11 or newer** (`requires-python = ">=3.11"` in `pyproject.toml`;
  CI verifies 3.11, 3.12 and 3.14; development runs on 3.14). 3.10 is not
  supported: current numpy and scipy publish no 3.10 wheels, so a 3.10
  install silently pins an older numeric stack than the one the audio
  processing is verified against.
* **ffmpeg and ffprobe on `PATH`.** The suite shells out to both:

  * ffmpeg — *decodes and encodes the audio formats the suite reads and writes*
  * ffprobe — *reads stream metadata (duration, codec, bitrate) for analysis tools*

  Install commands:

  ```
  Windows: winget install Gyan.FFmpeg
  macOS:   brew install ffmpeg
  Linux:   sudo apt install ffmpeg
  ```

  A missing binary is reported as a **warning at launch**, not a block:
  the `.pyw` launchers show which executables are missing and how to install
  them, and tools that do not shell out to ffmpeg keep working.

### Platforms

AudioSuite-Pro is **Windows-first**: the `.pyw` launchers, the CD Ripper's
Win32 SCSI pass-through and drive enumeration, and the `icacls` ACL hardening
in the shared key manager all target Windows. The CD Ripper is the only tool
with a Windows-only dependency.

The command-line core (`audiosuite ...`) has no Windows-only dependency of its
own, and the shared layer's platform-conditional code is small enough to
enumerate in full below. But **the suite has never been executed on a real
Linux or macOS host** — the Linux CI leg is still unrecorded — so read
everything left of the Windows column as *unproven in practice*, not as a
compatibility guarantee. The honest summary is: Windows is the supported
platform, and the matrix records which code paths are deliberately portable,
which are irrecoverably Windows-only, and which have simply never been
exercised.

#### What is verified, and what is not

**No tool in this suite has been executed on a real Linux or macOS host.** The Linux CI leg added by plan item A4 is still unrecorded, so "Portable core" below means *the non-Windows branch is implemented and covered by a test that runs it under a simulated platform value* — not that a foreign platform was ever exercised.

#### Tool tiers

* **Windows-only** — `cd_ripper`. The CD subsystem it drives (Win32 SCSI pass-through, drive enumeration) has no portable implementation; the tool fails fast with a named missing requirement rather than degrading silently.
* **Portable core** — the other 29 of 30 tools. Each has no platform-conditional code in its own package at all, so its non-Windows CLI path is the same code path as on Windows.

## Installation

Clone the repository, then sync the environment with the project's extras
(`dev` = the test/lint/typecheck gate, `analysis` = the librosa stack,
`cd-ripping` = discid/MusicBrainz for the CD Ripper):

```
git clone <this-repository> AudioSuite-Pro
cd AudioSuite-Pro
uv sync --extra dev --extra analysis --extra cd-ripping
```

Without `uv`, the equivalent is:

```
python -m pip install -e ".[dev,analysis,cd-ripping]"
```

The two ML tools need an optional fourth extra, `ml`: the Stem Separator pulls
Demucs and torch (2–3 GB on Linux because of the CUDA wheel set, hence not a
base dependency) and the ML Denoiser pulls RNNoise (13 MB, no torch). Nothing
else in the suite uses it, and without it each tool still opens, validates a run
and says what to install:

```
uv sync --extra dev --extra analysis --extra cd-ripping --extra ml
```

### One-command smoke test

```
uv run audiosuite --help
```

And a first working tool, in analysis-only mode (writes nothing):

```
uv run audiosuite normalise "C:\path\to\music" --dry
```

### Use the locked runtime

`uv run audiosuite …` is the supported way to run the CLI from this checkout:
it executes the dependency graph pinned in `uv.lock` against an editable
install of these sources, so the command list always matches the tree. A bare
`audiosuite` resolves whatever is on PATH — usually a global `pip install -e .`
from an earlier release. That install keeps the editable finder it was created
with, so once this tree gains a tool it dies with
`ModuleNotFoundError: No module named '<tool>'`. The CLI now prints that
diagnosis (and warns on every run whose installed metadata version differs
from `pyproject.toml`) with the two commands that fix it:

```
uv sync --frozen --all-extras
uv run audiosuite --help
```

If you deliberately use a global install, refresh its metadata after each pull
with `python -m pip install -e . --no-deps`; the version warning stops once it
matches `pyproject.toml`.

To check an install before blaming a tool, run `uv run audiosuite doctor`. It
reports the checkout and installed versions, resolves every first-party package
through the installed import machinery, lists any package that is missing or
comes from a different install, names each CLI command that gap would take
down, and exits 1 when anything is wrong (`doctor --json` publishes the same
findings as one document). It also names the interpreter a launcher would run
under — the project's `.venv` when one exists — and probes each tool's optional
engine (Demucs, RNNoise) in *that* interpreter, so "the extra is installed but
the tool cannot see it" is one line instead of a debugging session. A missing
extra is reported with its `uv sync --extra ml` fix and does not fail the
check: the first run that needs it offers the install. The CLI applies that
same origin rule at startup:
when a package in this checkout imports from another tree — which a rebuild at
the *same* version does — every command warns once per process and names the
packages, so a matching version is not mistaken for a current install.

The GUI path is the root launcher `Master_Driver.pyw` (a control panel with a
card per tool); every tool also has its own `<Tool>.pyw` launcher.

### Scripting the CLI

Every command accepts `--json` and then writes **one** JSON document to stdout,
when the run finishes: the counters, the run's log lines, and whatever the
command adds (`skipped_files`, `cue_path`, `packages`, …). Progress stays on
stderr and in the log. `audiosuite --json-schema` prints the machine-readable
contract, including a recorded success and failure example per command, so a
script can be written against real output.

There is deliberately no streaming mode (`--json-lines`): an hour-long batch
reports nothing machine-readable until it ends. A per-file stream would have to
be produced by every tool's progress callback, and the summary document is what
scripts consume; the one-document behaviour is locked by a test rather than left
to convention.

## Architecture

* **`audio_suite_shared/`** — the shared layer every tool builds on:
  manifest/plugin registration (`tool_plugin.py`), Tk styling and help
  launchers (`styles`, `ui_helpers`, `platform_utils`), secure subprocess
  execution (`secure_subprocess.py`, ffmpeg/ffprobe allowlist), startup
  preflight and declared system requirements (`preflight.py`,
  `system_requirements.py`), suite-wide JSON config (`suite_config.py`),
  the shared audio decode path for the analysis family
  (`analysis_loader.py`), and the exception hierarchy.
* **`BaseFileProcessor`** (`audio_suite_shared/file_processor_base.py`) —
  the common per-file workflow: progress callbacks, per-file error
  isolation (one bad file never aborts a batch), undo snapshots through
 `BatchUndoLog`, and the in-place DSP write path. Tools plug in a DSP
  callable and inherit the workflow.
* **Per-tool shape** — each `<package>/` contains `app.py` (Tk
  application), `core/` (DSP/analysis logic) and `cli.py` (click command
  registered on the shared `audiosuite` group); GUI-only extras live in
  `ui/`.
* **`master_driver/`** — the control panel: a card per tool
  (`ui/cards/{tool_id}_card.py`, the manifest `id` is the filename key), an
  arg builder (`runner/arg_builder.py`), and a batch orchestrator with an
  explicit dependency graph so parallel runs keep enrich → utility ordering.
* **Undo** — batch tag edits record an undo snapshot (`Undo_Tag_Edits.pyw`
  replays them); the configuration, keys and history live in the shared
  `audio_suite_config.json`.

## Engineering standards

The suite is held to a deliberately strict bar, so that a new contributor
inherits the same guarantees the existing tools have rather than discovering
them through review. Two properties are measured and enforced on every change:

* **Typing** — 99.5% of production definitions are fully annotated (99.9% of
  parameters) and `mypy` runs in `--strict` mode across the whole suite with no
  errors. Every public module, class and function carries a docstring; function
  signatures are explicitly typed end to end. The shared package's API
  reference is built from those docstrings: `uv sync --extra dev` (Sphinx is in
  the dev extra, and the build is a gate) then
  `python -m sphinx -b html docs docs/_build/html`.
* **Audio correctness** — this suite transforms users' audio, so any change
  that could corrupt, mis-normalise or mis-convert a file is the highest
  priority class of fix. Such changes are validated by decoding the result and
  measuring it, never by reading back the internal state the code just wrote. A
  fix that only proves self-consistency has proved nothing.

**The mandatory gate.** No change is complete until all six commands pass
(Windows/pwsh, from the suite root; the Python floor is 3.11):

```pwsh
# 0. compile / import gate — mandatory first step after any edit
python -m compileall -q -f . -x '(^|/)(\.venv|\.git)/'

# 1. lint + formatting
python -m ruff check .
python -m ruff format --check .

# 2. static typing (strict is set in pyproject.toml)
python -m mypy .

# 3. security screening (UTF-8 enabled on Windows; -c loads pyproject skips)
$env:PYTHONUTF8='1'; python -X utf8 -m bandit -r . -x ./.venv -c pyproject.toml

# 4. the full test suite — a package-scoped run is NOT a substitute
python -m pytest -q
```

Zero failures, zero "fix later": a failing test is never deleted, skipped or
`xfail`ed to turn the gate green — the cause is resolved. Coverage is
enforced on the bare full-suite run (`fail_under = 75`).

A defect found during any session is fixed in the same change that found it,
with a regression test alongside. Deferral is acceptable for new-feature
backlog items, never for a defect in working code.

`AGENTS.md` and `CONTRIBUTING.md` are the **normative** sources for these
rules — this section is a summary, and they win where the two differ.
`CONTRIBUTING.md` additionally documents the test-file naming convention, the
checklist for registering a new tool, and the `pytest -m hardware` opt-in for
the deselected hardware tests.
